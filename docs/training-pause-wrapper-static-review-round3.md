# Independent static review of the reversible training pause

20 October 2026. Reviewed `scripts/benchmark_factory_with_training_pause.py` before any process control by this reviewer. No suspend, resume, benchmark, NN or process test was performed. The coordinator and construction owner have agreed on the exact owned CPU trainer; this review addresses interruption recovery and whether measurements can honestly be called isolated.

The initial script correctly checked PID creation time, workspace cwd, training script, exact run name and a minimum RSS to distinguish the real Torch process from a small Windows environment launcher. It verified the frozen factory winner weights/metadata, refused to control an already stopped trainer, used a bounded watchdog, kept logs and put resume logic in `finally`. These checks are useful but did not close the following failure paths. Findings were sent to the coordinator before execution; the coordinator owns fixes and actual validation.

| Finding in initial reviewed version | Required correction |
|---|---|
| `suspend()` precedes `paused=True`; an interruption after successful suspension can leave the flag false and skip resume. `started` is assigned later, so another interruption can make `finally` raise before resume. | Initialize timer and ownership/attempt bookkeeping before suspension; resume the exact owned process after any pause attempt, with explicit state verification and exception-safe audit writing. |
| `Popen` returning does not prove the watchdog initialized successfully. Its stderr is suppressed. | Require tokenized ready acknowledgement and a live watchdog before suspension; monitor it during the block. |
| `CREATE_NO_WINDOW` hides the helper but does not establish survival outside a Windows parent job or process-tree cancellation. | Verify actual watchdog independence, or fail safely before suspension if the required breakaway launch is unavailable. Do not claim crash-survival guarantees from window flags alone. |
| `subprocess.run` timeout/interrupt may kill a small venv launcher while leaving its actual Python/NN child alive. Resuming training then creates contention and a stray workload. | Own/track each benchmark process tree; terminate and join that tree on failure before resuming the trainer. Never broadly kill unrelated Python or the training process. |
| Recorded stopped state and CPU totals were not enforced throughout; a watchdog could resume the trainer during a late phase. | Check stopped state, CPU quiescence and guard status before/after every phase. Reject timing if the watchdog fires, training CPU advances or state changes. |
| Phase timeouts sum to450seconds while the guard defaults to360seconds. | Use a global remaining-pause budget and reserve recovery margin; no benchmark may run across the watchdog deadline. |
| Marker files are read as JSON while ordinary writes can be partial. | Write markers atomically and handle transient parse failures without killing the resume watchdog. |

The first version's `cpu_before` was sampled before suspension and could count a small amount of legitimate work between sampling and suspension; a post-suspension CPU baseline is the appropriate isolation reference. A positive post-resume CPU delta helps demonstrate continued work, but cannot replace status/process-identity checks and honest error reporting if the trainer exits naturally or another error occurs.

The intended invariant is: the exact agreed trainer is resumed on every recoverable exit, benchmark children are gone first, and any loss of isolation invalidates speed conclusions. A separate watchdog is a recovery mechanism; its existence alone is not evidence that it will survive every host failure, process-tree kill or power loss. This is a static review record, not a claim that the corrected wrapper has already been exercised successfully.

## Implemented corrections and mocked verification

At the coordinator's explicit request, I updated the wrapper before any actual process control by this reviewer. It now initializes attempt/timer bookkeeping before suspension; uses atomic token-marker replacement; requires a live ready acknowledgement from the actual breakaway watchdog; verifies that watchdog's own `IsProcessInJob` result is false; and refuses any less-protected fallback if Windows denies `CREATE_BREAKAWAY_FROM_JOB`. A venv redirector's acknowledged interpreter must be a real descendant of the owned launcher. Exact training-script matching uses the full workspace path.

During the paused block, stopped state, post-suspension CPU consumption, guard liveness and guard-trigger markers are checked repeatedly and between phases. Remaining time reserves15seconds for cleanup/recovery. Benchmark launcher and actual interpreter descendants are tracked with creation times and terminated/joined on exit; reused/protected PIDs cannot be controlled. Recovery bookkeeping survives an interrupted successful suspend call, and a failed resume leaves the independent guard armed. Invalidated measurements cannot complete the block successfully.

`--probe-watchdog` performs only identity/readiness/Windows-independence checks, then disarms the helper. It neither writes a pause-attempt marker nor calls training suspend/resume. **No actual probe was run by this reviewer.** The coordinator must inspect the implementation and decide whether to execute the probe and subsequent actual block.

The two test files `tests/test_training_pause_identity.py` and `tests/test_training_pause_recovery.py` passed **24 mocked tests in1.19seconds**. All process objects and launches are fake. Coverage includes exact identity, malformed/stale markers, readiness failure, job/descendant checks, pause-budget exhaustion, CPU/status/watchdog invalidation, owned-child cleanup, protected/reused PID refusal, interrupted-suspend recovery and zero control calls in probe mode. These unit results do not establish that this Windows host permits breakaway or that an actual trainer has been suspended/resumed successfully.

## Coordinator's actual read-only probe

The coordinator subsequently ran the read-only probe. It **failed closed before any pause**: the actual watchdog reported that it remained inside a Windows job, and `pause_attempted` was false. The failed probe and its error artifacts must remain preserved. Unit tests did not predict or override that host result.

The coordinator proposed avoiding the Windows venv redirector by directly launching the trusted base Python interpreter with isolated/no-site startup and an explicitly supplied trusted export-environment site-packages path for psutil. The same breakaway flags, own-process job-membership check and ready handshake remain mandatory. This is an interpreter-launch change, not permission to accept a job-bound watchdog or modify host protections. At this note's update, no successful direct-interpreter probe or actual suspension is claimed by this reviewer; the coordinator owns that patch and any execution.

The coordinator implemented that direct-interpreter launch and executed the second read-only probe. It also reported `Watchdog remains in a Windows job`; its `pause_attempted` remained false. Both probe directories are retained under `output/optimization/factory-round3b/watchdog-probe*/`. The trainer was verified running with advancing CPU totals afterwards. No actual suspend/resume occurred, and final isolated benchmarks must wait for training completion.
