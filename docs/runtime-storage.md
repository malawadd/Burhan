# Local evidence retention and shutdown

`EventStore(root, max_events=1000, max_media_bytes=50*1024*1024)` stores event metadata in SQLite and optional JPEG byte evidence under `root/evidence`. It does not capture media itself. The runtime must explicitly supply evidence bytes when media saving is enabled.

`submit(profile, session_id, kind, payload, jpeg=None)` snapshots JSON and evidence bytes in memory before enqueue, preventing later caller mutation from changing capture provenance. It rejects NaN/Infinity, unsupported values, payloads above 256 KiB, identifier fields above 512 UTF-8 bytes, media above 5 MiB or above the configured media budget, a full 64-item queue, and an aggregate pending byte count above 16 MiB. `False` means rejection; `lost_events` and `error` explain the loss. JSON serialization and byte copies take CPU time; enqueue performs no filesystem or SQLite I/O and never waits for queue space. Callers should still submit small bounded metadata.

`start()` creates one writer and is idempotent. Submitting before start is supported. `close()` rejects further submissions, starts a drain if necessary, and waits up to five seconds. It returns the same fields as `status()`. `pending` includes queued and in-flight work; `queued`, `in_flight` and `pending_bytes` provide detail. `closed` means input is closed, not that persistence finished. `flushed` becomes true only when outstanding work is zero and the writer has ended. `flush_timed_out` signals a writer still running after the bounded join. A later `close()` can wait again. Pending work can be lost if the process exits while this daemon writer is still active; the runtime must report that outcome. Flushed work can include explicitly counted failed writes: also inspect `lost_events` and `error`.

Payload snapshots are immutable encoded JSON, not live dictionaries. `created_at` is UTC submission time. It is not the source capture time. The caller must include source ID, frame sequence, source timestamp, capture monotonic time, profile/configuration identity and synthetic/demo origin in the payload when required; the store does not fabricate provenance.

The writer reserves media space before writing, uses a temporary file followed by rename, then commits metadata. Failed inserts remove uncommitted media. Startup and post-write reconciliation enforce the event-row limit, remove unreferenced `.jpg`/`.tmp` evidence, clear missing references and enforce the JPEG byte budget. The evidence directory is dedicated to this store: unrelated files with these extensions should not be placed there. Old media can be removed while its event metadata remains, represented by `media_name: null`. Metadata row limits and JPEG limits are separate; SQLite pages, WAL files, filesystem allocation and external files are not covered by the JPEG byte cap. Permission errors or a full disk can prevent cleanup; these failures surface in `error`, rather than being claimed as successfully bounded storage.

Each database context commits/rolls back and explicitly closes its connection, including exceptions. This avoids Windows file handles surviving until garbage collection. Only a single EventStore writer should manage a given root; multiple processes sharing a directory are outside this implementation's coordination contract.

Regression tests cover snapshot immutability, invalid JSON, queue byte/item caps, startup cleanup, row/media retention, rollback orphan cleanup, Windows-compatible handle release, shutdown timeout reporting and post-close rejection. Run `.venv/Scripts/python.exe -m unittest discover -s tests -p test_storage.py -v`.
